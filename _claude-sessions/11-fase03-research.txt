| TD | Escopo | Decisão | Recomendação |
|---|---|---|---|
| 01 | Backend | Tecnologia da fila | BullMQ + Redis. pg-boss fica como alternativa se você quiser evitar um serviço novo. |
| 02 | Cross-layer | Upload de até 10GB | Multipart S3 com URLs pré-assinadas por parte. |
| 03 | Cross-layer | Buckets e chaves | Um bucket privado, com chaves `videos/{uuid}/…`. |
| 04 | Repo-wide | Runtime do worker | Mesma base NestJS, outro entrypoint e outro container. |
| 05 | Backend | FFmpeg, metadados e thumbnail | Chamar `ffprobe`/`ffmpeg` direto sobre uma URL pré-assinada, com download para disco como fallback. |
| 06 | Cross-layer | URL única | Id aleatório de 11 caracteres com constraint `UNIQUE`. |
| 07 | Cross-layer | Streaming e download | O API devolve um redirect para uma URL pré-assinada; o storage responde 206. |
| 08 | Backend | Ciclo de status e falhas | `processingStatus` separado da publicação, com retry e backoff, depois `FAILED` com motivo. |

Pontos que valem sua atenção:
- **Upload de 10GB:** um PUT pré-assinado simples ficou de fora, porque o S3 limita um PUT a 5GB.
- **Endpoint do storage:** as URLs pré-assinadas precisam usar um endpoint acessível pelo navegador, diferente do `minio:9000` interno usado pelo API e pelo worker. Registrei isso na TD-02.
- **`fluent-ffmpeg`:** o `npm view` retorna "Package no longer supported", então não o recomendo.
- **`nanoid` v6:** é ESM-only e o backend usa `module: nodenext`, então a TD-06 sugere gerar o id com `crypto` se houver atrito.
- **Frontend:** não tem TD próprio, porque a Fase 03 não lista telas. Ele entra só pelos contratos cross-layer (TD-02, 03, 06, 07), e isso está justificado no cabeçalho do documento.
